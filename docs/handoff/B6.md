# B6 Words track and placement
Status: done

## What was built
The real `words` and `placement` modules (`apps/api/src/modules/words/`, `apps/api/src/modules/placement/`) behind their 8 endpoints. No contract stub is left.

| Piece | Where |
|---|---|
| `GET /words/bands`: three bands of 1,000 ranks (1-1000, 1001-2000, 2001-3000) with total, known, learning, unknown | `words/service.ts` `bands`, `words/repo.ts` `countBand` |
| `GET /words`: one band (or ranks 1-3000 without `band`), `status` filter, keyset paging by (rank, id), cursor `<rank>.<lemmaId>` | `list`, `repo.listWords` |
| `POST /words/triage`: up to 200 decisions in the handler's one transaction; known and ignored go to `NotesPort.setLemmaStatus` (one call per status), learn goes to `NotesPort.createWordNote` (source `words`) plus one `setLemmaStatus(..., 'learning', 'triage')` | `triage` |
| `PUT /lemmas/:id/status`: `learning` creates the word note, every status is set through `NotesPort` with source `manual` | `setStatus` |
| `GET /lemmas/:id`: lemma, senses, table of forms from `MorphologyPort.getParadigm(id, tx)`, up to 10 sentences with the lemma's span, status, the learner's live word note id | `lemmaDetail` |
| Placement rules (pure): seeded sampling, strata, wrong options, case round choice, result | `placement/items.ts` |
| `POST /placement`, `POST /placement/:id/answers`, `GET /placement/:id`; grading, applying the result | `placement/service.ts`, `placement/repo.ts` |

Placement run, as built:
- Rounds 1 to 3: 12 vocabulary items each over six strata of 500 ranks. Round 1 takes two per stratum; rounds 2 and 3 take 12 from the first stratum with a miss and its neighbours (split evenly, remainder to the missed stratum; the top stratum when nothing was missed). A stratum out of unseen words passes its share to the nearest stratum. No word is asked twice in a run. Candidates are ranked lemmas with a gloss, not retired, not proper names.
- An item's options: the right gloss and 3 wrong glosses, shuffled, then `I don't know`. Wrong glosses come from the 8 nearest lemmas by rank with the same part of speech (others only when too few share it); duplicates and the right gloss are skipped.
- Round 4: the case round, two `cloze` exercises per teaching lesson (declension lessons with a case or a number, in course order: 8 in the mini set; `mixed` is not one), the two closest to difficulty 0.5, then single word gaps, verified, id. The gap is written `___` in `sentenceSk` and `blank` points at it.
- `items` of `app.placement` stores each item with its key, the answer given and, for case items, the attempt to log. Randomness is seeded by run id and round, so a run's rounds depend only on its id and its answers.
- Result: `knownUpToRank` = 500 × the leading strata with ≥ 85 % right; a lesson is tested out when all its gaps (both) are right; `startLessonId` = the first course lesson not tested out (`mixed` when all eight are).
- Applying, in the transaction of the last answer: `NotesPort.setLemmaStatus(known, 'placement')` for ranked lemmas up to `knownUpToRank` whose status is still unknown (no row or `unknown`), `tested_out` rows in `lesson_progress` for lessons without a row (`on conflict do nothing`), `current_lesson_id` and `placement_done_at` on the profile (written only when different), and the case attempts through `AttemptsPort.record` (source `placement`, `sourceRef` the run id, with diagnosis and error type from `@app/ling`).
- Repeats: `POST /placement` with an id the learner owns returns the stored run. An answered round sent again with the same answers returns the same next round (or the result); other answers are `409 conflict`; a round not given yet is `409`.

## How to run and test it
`pnpm test --filter api` (or `npx vitest run src/modules/words src/modules/placement` in `apps/api`), `pnpm check`.

- `words/words.test.ts` (one database: mini set + generated lemmas ranked 73-2500): bands and their counts after sorting; paging a whole band in rank order (5 pages of 200); status filter; bad cursor and band; **200 words sorted in one transaction** (one `withUser`, every port call on the same `tx`, 50 notes for the 50 learn decisions only, one status call per status, rows in `user_lemma`; repeat creates no note); a failing port half way leaves no row; later decision wins; unknown lemma → 400; **the word page of *mesto* has every case except the vocative in both numbers** (`meste` loc sg, `miest` gen pl, `mestami` ins pl); status and note id after learning; all 72 mini lemmas answer within the contract; 404s; isolation.
- `placement/items.test.ts` (pure, generated candidates for 3,000 ranks): two per stratum in round 1, items without answers, determinism, wrong options with same part of speech and similar rank, fallback, the window around the first miss (also clipped and top), a short pool, the 85 % rule, 16 medium gaps two per lesson, the `___` gap, tested out lessons and the start lesson.
- `placement/placement.test.ts` (one database: mini set + generated lemmas ranked 73-3000): **three simulated learners** through the HTTP API: knows the first 1,000 words → `knownUpToRank` 1000, start `acc-sg`, 1,000 known rows, 16 logged attempts; knows nothing → 0, no rows, no attempts; knows everything → 3000, all eight lessons tested out, start `mixed`. Same answers → same next round, other answers 409, items of another round and missing options 400, replaying the last round returns the same result and **changes nothing**; **`applyResult` twice changes nothing more** (rows, profile, attempts, no status call); the learner's own statuses and lesson rows are kept; a failure while applying leaves nothing applied and the run active; isolation.

Simulation: the mini dataset has only 72 lemmas ranked 1-72, so the tests add plain lemmas `w<rank>` (id 100000 + rank, part of speech cycling noun/verb/adj, gloss `gloss <rank>`) for the ranks after it as the table owner (`testing/lemmas.ts`). The simulated learners read each item's key from `app.placement.items` as the table owner (the API never sends it).

The three backend checks:
- Every response parses with its contract schema: the route helper validates every response in tests, and the tests also parse with the schemas.
- Isolation: on the placement endpoints learner B gets `not_found` for A's run (`get`, `answer`); the words endpoints hold no learner row ids, so the test shows B sees none of A's statuses or notes in bands, the list and the word page, and B's write leaves A's row alone.
- This package provides no port, so no port suite applies.

## Differences from the specification, and why
- **Bands are 1,000 ranks wide** as the specification and the architecture say; the F2 example of `words.bands` shows 500-wide bands. `total` is the number of ranked, not retired lemmas in the band, not a fixed 1,000.
- **Ignored words** are in a band's `total` but in none of `known`, `learning`, `unknown` (the contract has no ignored count).
- **Learn also sets `learning`** through `NotesPort.setLemmaStatus`, so the status is right whether or not `createWordNote` sets it.
- **Four meanings per item** (one right, three wrong) plus `I don't know`; the F2 example shows two meanings, the specification fixes no number.
- **`POST /placement` with another learner's id is `409 conflict`**, not 404: the row exists but row level security hides it, so it can be neither created nor shown. Ids are client UUID v7, so this only happens on purpose.
- **Missing answers count as wrong.** Attempts are logged only for case items with a typed answer.
- **Placement items in a round are ordered by rank**; the case round by lesson order.
- `diagnoseForm` gets the form map of the target lemma but no `siblingEndings`, so a wrong pattern ending is logged as `not_a_form`.
- After merging the updated project branch, the word page's table of forms comes from `MorphologyPort.getParadigm(id, tx)` (build lead's request); everything else on it is read in `words/repo.ts`.

## Known gaps and follow ups
- **`pnpm check` fails in the shared F5 contract test** (`apps/api/src/app.test.ts`, not B6's to change): it calls `placement.get` and `placement.answer` as a new learner with the example run id, and the real module answers `404 not_found` in the error shape, as it must for a run the learner does not own. Needed shared change: in that test, start a run as the same learner before these two calls, or accept a `not_found`/`conflict` error response that parses with `ErrorResponseSchema` for endpoints that address a learner's row by id (the same will hit the notes, texts and tutor endpoints once B1, B4 and B9 merge). Everything else in `pnpm check` passes (typecheck, lint, deps check; one web test, `ChatScreen.test.tsx`, failed once under machine load and passes alone).
- The tests use the F5 recorders for NotesPort and AttemptsPort. Because the recorder keeps statuses in memory, both modules carry a small test double (`<module>/testing/db-notes.ts`, the same file twice, as modules may not import each other) that also writes `user_lemma` and a bare word `note` row. I1 should run the words and placement tests once more with B1's real NotesPort and B5's real AttemptsPort.
- Glosses missing from the dictionary are not fetched (no model call inside the transaction); `glossEn` is null in the list, and such lemmas are not used in placement.
- No `abandoned` transition: nothing in the contract abandons a run.
