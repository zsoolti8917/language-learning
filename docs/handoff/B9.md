# B9 Tutor module
Status: done with gaps

## What was built
All eight `/tutor` endpoints on real data, the six step turn pipeline, and version 1 of the prompts `tutor.analyze`, `tutor.reply` and `tutor.summary`.

| File (`apps/api/src/modules/tutor/`) | Holds |
|---|---|
| `routes.ts` | The eight handlers. |
| `service.ts` | Scenarios, start (opening line as message 0, a repeated id returns the stored detail), list (cursor on `updatedAt`, id), open, the turn (`sendMessage`, `runTurn`), peek, end, dispute; the views (`toTutorError`). |
| `analysis.ts` | `TutorAnalysisSchema` (the contract's `TutorAnalysis`, owned here), `analyzeMessage` (step 2), `normalizeAnalysis`. |
| `verify.ts` | `verifyError`, `verifyErrors` (step 3) through `MorphologyPort`, `findTrigger`, the `ErrorTarget` of a case error (lemma, case, number, gender, pattern, cue, answer). |
| `decide.ts` | `decideTurn` (step 4: the decision table and the reply directive), `suggestQuestion`, `checkReply` (rule checks on a reply), `MAX_PROMPTS` 2, `MAX_TURNS` 40. |
| `prompts.ts` | The requests of the three routes: the folder's blocks plus the scenario block, the user messages, `renderDirective`, `promptVersionLabel`. |
| `cards.ts` | `caseSentenceContent` (the corrected sentence with the corrected words blanked) and `tutorAttempt`. |
| `repo.ts` | All SQL, including the one `content_report` insert for a dispute. |
| `pipeline.ts` | One import for the evals: every step above. |
| `steps.test.ts`, `tutor.test.ts` | Tests (below). |

Prompt folders (`packages/ai/prompts/tutor.*`): v1 of each, plus local mode mocks for `tutor.analyze` (finds *s kamarát* and *do mesto* in the mini scenario, so `pnpm dev` shows a prompt) and `tutor.summary`. `tutor.reply` keeps F5's mock line.

A turn: transaction 1 loads conversation, scenario, messages, errors and triggers and checks the limits (repeat, ended, 40 turns, 20 messages a minute) before the stream starts. Then, with no transaction open: `tutor.analyze` → `verifyErrors` → `decideTurn` → `analysis` event → `tutor.reply` streamed as `delta` events. Transaction 2 stores both messages, the errors, statuses of earlier errors, notes through `NotesPort`, attempts through `AttemptsPort` and the goal; then `done`. Any failure becomes one `error` event and stores nothing. The turn runs through `runInBackground`, so it completes when the client goes away (`waitUntil` on Vercel). Keep alive every 15 s (`KEEP_ALIVE_MS`).

Decision table as built:
- New verified case error: `prompted`, at most two per message by position, and a wrong first try attempt. Later ones are `summary_only` (verified), get the attempt too, and become cards at the end.
- Open prompted error: `self_corrected` when the model reports it fixed or the expected form is in the new message (correct attempt, `retry: true`); otherwise `corrected` (missed, repeated, or not tried) with a case sentence note and a wrong attempt (`retry: true`). Prompted errors live for one turn.
- Unverified case error and every other slip: `summary_only`. A dropped error (given form valid for the case, or nothing changes) is not stored; the learner message's `annotations.dropped` counts them.
- A message the model cannot understand prompts nothing.
- Peek: `hint` is built from data without a model call (case, trigger, a question, the pattern's ending); `answer` sets `corrected`, logs a wrong attempt and makes the card; `translate` uses `tutor.reply` with `task: translate` and caches the text in the message's `annotations.en`.
- End: still prompted errors become `corrected` with a card; checked `summary_only` case errors get a card; `tutor.summary` writes `textEn` (no model call when the learner wrote nothing); a repeat returns the stored summary.
- Dispute: status `disputed`, `NotesPort.suspendNote`, and one `content_report` (`target_kind 'tutor_error'`); a repeat changes nothing.

## How to run and test it
`pnpm test --filter api` or `pnpm --filter @app/api exec vitest run src/modules/tutor` (about 12 s), `pnpm check`. Try locally: `pnpm dev`, start `scn-city-walk`, write *Dnes idem do kina s kamarát.*

- Script one (`tutor.test.ts`, "script one"): prompted without `expected`, fixed → `self_corrected`, no note, attempts wrong first try + correct retry.
- Script two: two misses → `corrected`, exactly one case sentence note (`Potom ideme do mesta.`, blank 15–20, answers `mesta`, gen sg n, `prep-do`), `done.cardsCreated` holds its id.
- A reported error whose given form is correct is dropped (nothing stored, nothing in the stream). An expected form that does not exist (`kamarátem`) is never in the stream, the detail, the end summary or the reply prompt, and never becomes a card; revealing it is 409.
- Events in order (`analysis`, `delta`…, `done`), every event parsed with `TutorStreamEventSchema`; a repeated `clientId` replays the stored turn with no model call; another text with the same `clientId` is 409.
- "no model call starts while a transaction is open": the test database counts open `withUser` transactions, and every gateway call of the file records the count (all 0).
- Dispute suspends the note and stores one content report.
- Also: keep alive (fake `setInterval`), client disconnect still stores and the retry replays, 1,000 characters, 20 a minute, 40 turns, budget and model failures as `error` events, at most two prompts, end and repeat end, peek kinds, paging.
- Backend checks: responses are validated against the contract by the route helper in tests; isolation test (learner B gets `not_found` on get, send, the three peeks, end and dispute; list empty). B9 provides no port.
- `steps.test.ts`: verification on the mini dataset (mesta/mestá, phrases, `s`→`so mnou`, triggers), normalisation, the decision table, cards, and that system blocks are equal across turns with no dates or ids.

## Differences from the specification, and why
- `TutorAnalysis` has one more optional field per error, `correctedSentenceEn`, for the card's `sentenceEn` (the contract's `CaseSentenceContent` needs one). Without it `sentenceEn` is empty.
- "A second miss becomes corrected": a prompted error the learner does not try again in the next message also becomes `corrected`, so no error stays open across turns.
- Revealing an answer also makes the card, like any other `corrected` error.
- An unverified case error never shows `expected`, `correctedSentence` or `explanationEn` (the explanation can name the unchecked form), also in the end summary. M6 shows "not checked" for it.
- `tutor.startConversation` with an id another learner owns answers 409 (the id is taken), not 404.
- Budget exhaustion during a turn is an `error` event in a 200 stream (the contract example); other checks (404, 409, 429, 400) answer as JSON before the stream.
- The scenario block is built in `modules/tutor/prompts.ts` (prompt folders hold only stable blocks); the version of each route is stored in `conversation.prompt_version` as `tutor.analyze@1 tutor.reply@1 tutor.summary@1`. History is sent as a transcript inside one user message, so the request never starts with an assistant turn.
- `tutor_error.note_id` is set with `(select id from app.note where id = …)`: with the notes stand in (no row) it stays null instead of breaking the foreign key. The tests use a notes port that also writes the `app.note` row.
- The work started in the shared checkout by mistake; the lead's merge of `wp/m2-review` briefly landed on `wp/b9-tutor` and was moved back. The branch now merges `claude/project-thread-vaaf7g` (B2 lexicon, port `tx` arguments, contract test change).

## Known gaps and follow ups
- Prompts are untuned (I3). The reply is not filtered after streaming; `checkReply` reports leaks for the evals only.
- With the notes stand in (until B1), notes are not in `app.note`, so `note_id` stays null, `cardsCreated` of `/end` counts 0 and a dispute cannot suspend.
- Peek `translate` uses the `tutor.reply` route (no own route in `AiRoute`).
- Not run against the real gateway (B8) or Postgres.

## Notes for packages that depend on this one
- I1: the stream follows M6's expectations: `analysis.messageId` is the stored learner message id, `done.tutorMessage.content` is the stored reply, a retry with the same `clientId` and content replays without storing twice. Content is NFC trimmed before storing; error offsets are UTF-16 units of that text.
- I3, running the steps directly (`import … from '@app/api/modules/tutor/pipeline'`), none opens a transaction:
  ```ts
  const ctx: TurnContext = { scenario, history: [], openErrors: [], criteria: [], message };
  const { analysis, usage } = await analyzeMessage(gateway, userId, ctx);    // tutor.analyze + normalizeAnalysis
  const { kept, dropped } = await verifyErrors(analysis.errors, { morphology, triggers });
  // kept[i].outcome: 'verified' | 'unverified' | 'other'; dropped = false corrections removed
  const decision = decideTurn({ ctx, meaningOk: analysis.meaningOk, retries: [], goalUpdates: [], errors: kept, open: [], triggers, turnCount: 0 });
  const req = replyRequest(ctx, decision.directive);                         // then gateway.stream({ ...req, userId, onText })
  checkReply(text, decision.directive, hiddenForms);                         // 'no_question', 'leaked:<form>', 'too_long', 'markdown'
  ```
  `morphology` is the real `createMorphologyPort(ctx)` of B2 (or `createMiniMorphology()` in tests); `triggers` are `ling.trigger` rows as `{ id, kind, lemma, case, meaningEn }`. `analyzeRequest(ctx)` gives the raw request without calling. The system blocks per route are `systemFor(route, scenario)`.
- New prompt versions: add `v2.ts` in the folder and point `current` at it; the scenario block is appended by `systemFor`.
