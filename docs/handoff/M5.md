# M5 Words track, word page and placement
Status: done

## What was built
Everything lives in `apps/web/src/features/words/` and `apps/web/src/features/placement/`.

| Path | Holds |
|---|---|
| `words/WordsScreen.tsx` | `/words`: the bands with a progress ring (known of total), counts per status, the learner's band target |
| `words/BandScreen.tsx` | `/words/band/$band`: the words of a band with a status filter (Tabs: All, New, Learning, Known, Ignored), paging with "Show more", and the button into sorting mode |
| `words/SortSession.tsx` | Sorting mode: one new word at a time, meaning hidden until asked; Known, Learn, Ignore by button or swipe (right, left, up, 80 px); Undo; a counter; offline from the last fetched deck |
| `words/triage.ts` | `TriageBatcher`: decisions to the outbox in batches of 20, the last decision always undoable, the waiting batch kept in `kv` and sent on leaving (unmount, `pagehide`, page hidden) or on the next start |
| `words/LemmaScreen.tsx` | `/lemma/$lemmaId`: glosses with a "machine written" mark (`source` generated or runtime), the table of forms, examples with the form marked, the status control, and the link to the note |
| `words/paradigm.ts` | `buildParadigm(forms, topForms)`: six cases by singular and plural (one column for pronouns without number), the most used forms, a vocative that differs from the nominative, forms without case |
| `words/states.tsx` | Loading, error and offline states of the words screens |
| `words/messages.ts`, `placement/messages.ts` | All interface text (`defineMessages`) |
| `words/mocks.ts`, `placement/mocks.ts` | Feature mock handlers: bands, lists, triage, word pages for all 72 mini lemmas with statuses in memory; a graded placement run (3 × 6 words, 8 typed gaps) kept in `sessionStorage` |
| `words/mockData.ts`, `placement/mockData.ts` | Generated from `packages/testkit/mini` (lemmas, senses, forms, sentences, cloze exercises). Nothing hand written |
| `words/mockHttp.ts` | `featureMock(name, resolver)`, `errorResponse`, `enableFeatureMocks(on)` (see Differences) |
| `placement/PlacementScreen.tsx` | `/placement`: introduction, three vocabulary rounds (choices, the last is "I don't know"), one case round (AnswerInput, "I don't know", no feedback), a progress bar across the four rounds, the result, and "Go to Today" |
| `placement/run.ts` | The run kept in `kv` (`placement.run`) after every answer; `progressOf`, `roundAnswers`, `markPlacementDone` |
| `words/e2e/`, `placement/e2e/` | Playwright at 390 × 844 against the mock server (own config, port 5185) |

## Differences from the specification, and why
- **Feature mocks do not import `src/mocks/handlers`.** `handlers.ts` loads `features/*/mocks.ts` eagerly, so a feature mock that imports `mockEndpoint` from it (as F6's note says) runs before `handlers.ts` is initialised; under Vitest every suite fails with "Cannot access … before initialization". `words/mockHttp.ts` rebuilds the same URL pattern from `ENDPOINT_META` and `env` without the cycle.
- **Feature mocks are off under Vitest unless a test switches them on.** F6's `src/lib/api/client.test.ts` expects every endpoint to answer its contract example, while F6's note says feature handlers win in tests too; both cannot hold. M5's handlers answer nothing when disabled, so MSW falls through to the example handler. In the browser (mock mode) they are on; M5's own screen tests call `enableFeatureMocks(true)`.
- **Batches of 20 are separate outbox items** (`enqueue(…, { merge: false })`); otherwise the outbox would merge waiting batches into one of up to 200. A full batch is handed over when the 21st decision arrives, so the last decision is always in the waiting batch and can be undone.
- **The table shows six cases** (no vocative row), as the Done when asks. A vocative that differs from the nominative (*chlap → chlape*) is listed under the table.
- **The word page's `<h1>` is the screen title "Word"** (small, above the lemma), because F6's route tests and smoke run look for the screen title as the level 1 heading. The lemma itself is the large line below it.
- **placementDoneAt**: the server sets it when it applies the result (contracts, "Placement"). When the result arrives the client writes `placementDoneAt` (only if empty) and `currentLessonId` into the cached profile (query cache and `kv` `profile`, as `loadProfile` keeps it) and marks profile, today, words and course stale, so the first run guard (`isFirstRun`) lets the learner into Today at once.
- The progress bar across the rounds is a small token styled element with `role="progressbar"`; the design system has only a ring.
- The mock rounds are smaller than the real ones (6 words per vocabulary round, 8 typed gaps instead of 12 and 16) to keep the tests short; the client takes whatever the server sends.
- Lesson names on the result come from `GET /declension/course`; an id that the course does not list is shown as is.

## Notes for packages that depend on this one
- Today (M1) can link to `/placement` for the first run and to `/words` for word progress; `words.bands` gives the counts.
- The reader (M3) can link a word to `/lemma/$lemmaId`. The word page writes the server's status into the local `lemmaStatus` table on every load, and a status change goes through the outbox (`lemmas.setStatus`), whose applier updates `lemmaStatus`.
- Sorting writes `lemmaStatus` at once (`known`, `learning`, `ignored`) and puts the old value back on undo.
- Local keys: `kv` `words.triage.waiting` (the waiting batch), `words.sortDeck.<band>` (the deck for offline sorting), `placement.run` (the running placement).
- I1: the placement result screen moves on with `navigate({ to: '/' })` and relies on the profile cache patch described above; with the real API the server's own `placementDoneAt` replaces it on the next profile fetch.
