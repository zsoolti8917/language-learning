# I4 Offline, sync and install hardening
Status: done with gaps

## What was built
- **Offline suite** `e2e/offline/` (`pnpm e2e:offline`): 17 Chromium tests at 390 x 844. They run
  against the same servers as I1's flows: the production client build with its service worker,
  and the real API in local mode (PGlite, dev login, mock gateway, response validation). Every
  test uses I1's fixtures: a fresh learner, a contract check of every `/api/` answer, and a
  failure on any console error or 5xx. `support.ts` adds:
  - an extended `test` that expects `ERR_INTERNET_DISCONNECTED` while the test is offline;
  - raw IndexedDB reads and writes of the client's tables (`readStore`, `outboxRows`,
    `addOutboxRow`, `localQueue`);
  - `swControls` (the service worker controls the page);
  - review helpers.

- **Fixes in `apps/web/src/lib/`:**
  - *Expired login kept the outbox (data loss fix).* Before, a 401 that no refresh could fix
    called `signOut()`, and `signOut()` wiped the local database. Answers given offline were
    lost when the login had expired in the meantime. Now `AuthStore.refreshAfterUnauthorized`
    calls `expire()`: it signs the page out and clears the query cache, but keeps the rows.
    `claimLocalData(userId)` (`lib/db/storage.ts`) records the owner in kv `auth.owner`. Each
    session (at start, sign in, verify) is claimed before the app switches to it. Rows of
    another learner are removed first. A sign out on purpose still wipes everything. After a
    fresh sign in, the store asks for persistent storage and runs `outbox.syncNow()`.
    `AuthStore` takes an optional `localData` hook object (defaults to the above) for tests.
  - *Outbox never sends without a login.* `Outbox` takes `canSend` (`lib/db/index.ts` wires it
    to `hasLogin()` from `lib/api`). While nobody is signed in, items wait (`stopped:
    'signedOut'`). Each outbox call also passes the new `CallOptions.requireLogin`. A login can
    expire during a run, because another request's 401 signs the page out. In that case the
    client fails the call locally with a 401 instead of sending it without a token. The repeated
    e2e runs caught exactly that case.
  - *Retry after a network failure while online.* Before, a run stopped by a network error
    waited for the next trigger (`online`, foreground, a write). If the `online` event came
    before the connection worked, as it can on a phone and in Chromium, nothing was sent until
    the next trigger. Now the outbox tries again by itself after 2 s, doubling up to 60 s
    (`networkRetry` option), while the device reports online. The trainer and update tests were
    flaky without it.
  - *Refused items.* `Outbox.retry(seq)` and `Outbox.failedItems()`. `SyncIssues` in
    `lib/pwa/notices.tsx` lists each refused write with a label ("Review answers (3)", "Word
    status", …), the server's message, "Try again" and "Discard". It is part of `PwaNotices`,
    so it shows on every tab screen.
  - *Storage.* `lib/db/storage.ts`: `canOpenLocalDatabase`, `checkLocalDatabase`,
    `useLocalDatabase`, `requestPersistentStorage`, `claimLocalData`. `StorageNotice` (in
    `PwaNotices`) shows `notices.storageUnavailable` when IndexedDB is missing or refuses to
    open.
  - Unit tests: `lib/db/storage.test.ts` (new), `lib/pwa/notices.test.tsx` (new), plus cases in
    `lib/db/outbox.test.ts` (canSend, retry/discard, a `sending` row left by a closed page, a
    retry after a network failure), in `lib/api/client.test.ts` (`requireLogin`) and in
    `lib/auth/auth.test.tsx` (expiry keeps rows, sign out clears, claim at start, a broken
    database does not block sign in).
- **Phone checklist** `docs/acceptance.md`, section "iPhone checks (I4)": the install hint and
  installing, safe areas, the keyboard and the accent bar, zoom on input fields, plus offline,
  storage and update checks that only a real phone shows.

## How to run and test it
- `pnpm e2e:offline` runs the suite (free ports, its own build). Use `pnpm e2e:offline --
  --repeat-each=3`, or `pnpm e2e:offline -- hard-moments -g expired` for one test. To reuse a
  build: `E2E_SKIP_BUILD=1 E2E_DIST_DIR=<dir> pnpm e2e:offline`. Results go to
  `e2e/test-results/offline`.
- `pnpm check` passes.
- Results on 2026-11-17 (cloud container, 4 cores under load): `pnpm e2e:offline --
  --repeat-each=3` passed twice in a row, 51 of 51 each time (about 3 minutes). The I1 flows
  passed with these lib changes, apart from the flaky I1 test below. The two device test takes about 70 s because it waits
  for the card's one minute learning step. Its timeout is 7 minutes.
- CI: the `browser` job also runs `pnpm e2e:offline -- --repeat-each=3`, and its timeout went
  from 45 to 75 minutes.

## Differences from the specification, and why
- **"Virtualised lists".** Only the reader's text is virtualised (`VirtualText`, M3). The deck
  and the word band lists are paged (50 per page), not virtualised. The suite checks both
  behaviours and changes neither (not in scope: new features).
- **Two devices "converge after syncing".** The device that syncs first holds the server state
  from before the other device's answer until it fetches the queue again. A card shows in the
  queue only once due, so the test waits for the learning step (about 60 s) and then compares
  the fetched states. The server's replay itself is checked right after both syncs.
- **The update test** uses its own static server, not `vite preview`. Playwright's
  `context.route` does not intercept the browser's fetch of the service worker script, and
  changing `sw.js` in the shared build would show the update to parallel tests.
- **The expired login** is simulated by answering 401 to every API call (dev tokens never
  expire), and "signing in again" restores the learner's dev session. In dev mode the one tap
  login is a fixed user, so it would count as another learner and clear the rows. A unit test
  covers that case.
- **The refused write** in the e2e test is written straight into the outbox (`addOutboxRow`, the
  same row shape `Outbox.enqueue` writes) as a status for a lemma the server does not know. No
  screen can produce a write the real API refuses on demand.
- `docs/acceptance.md` belongs to I6. I4 created it with its own section, as the "Done when" of
  I4 asks.

## Known gaps and follow ups
- **Changes outside the owned paths** (each small, in its own commit):
  - `apps/web/src/messages/en.ts`: the shell texts `notices.storageUnavailable`,
    `notices.sync*` and `syncItems.*`.
  - `e2e/scripts/run.mjs`: `E2E_CONFIG` picks the config (default unchanged).
  - `e2e/tsconfig.json`: includes `offline`.
  - `e2e/package.json` and the root `package.json`: script `e2e:offline`.
  - `.github/workflows/ci.yml`: the offline step and the job timeout.
  - `docs/acceptance.md`: see above.
- No API change was needed: deduplication of repeated answers and the replay of older answers
  already hold (B3).
- Switching learners after an expired login is not race free in one case. If the outbox sends
  at the very moment another learner signs in, before the claim has cleared the rows, an old
  item could go out under the new token. The window is a few milliseconds and needs an expired
  login followed by a different account on the same device.
- The e2e tests answer the review cards and then poll the outbox. An answer is stored in the
  outbox just after the screen moves on, not before.
- **Flaky I1 test, not edited (not my path).** `e2e/flows/review.e2e.ts`, "review session",
  goes back online right after the third offline answer. Sometimes that answer is not in the
  outbox yet, so it goes in a second batch, and the test expects one batch with both answers.
  This failed 1 time in 6 runs here, and 4 more runs passed. Fix: before
  `setOffline(false)`, poll the outbox (or the "waiting" line) until both answers are there.
  `e2e/offline/support.ts` (`outboxRows`, `answersIn`) has the helpers.
- A sign out on purpose still drops unsent writes, as the specification says ("local data wiped
  on sign out"). Settings could warn when `useOutbox().pending > 0` (M1's screen).
- The performance limits are generous on purpose: the test machines are busy. They catch a
  regression of several seconds, not a small one.
- Supabase mode is untested here, as before (F8). There, `expire()` calls the client's
  `signOut`, which may fail with an expired token. The failure is caught.
- No new dependencies.
