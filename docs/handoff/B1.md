# B1 Review engine and notes
Status: done

## What was built
The learner's deck and review queue in `apps/api/src/modules/notes/` and `apps/api/src/modules/review/`, replacing the F5 stubs and the notes recorder.

| Piece | Where |
|---|---|
| `/notes` endpoints: list (kind, `q`, cursor), get, create, update, delete | `notes/routes.ts`, `notes/service.ts` |
| The real `NotesPort` (`createWordNote`, `createPhraseNote`, `createCaseSentenceNote`, `suspendNote`, `setLemmaStatus`) | `notes/port.ts` (uses `notes/service.ts`) |
| Word note content: sentences for the lemma's top forms, capture, fallbacks | `notes/service.ts` `buildWordContent` |
| SQL of notes, cards, `user_lemma`, and the `ling` reads (lemma, sense, form, lemma_sentence, sentence) | `notes/repo.ts` |
| `GET /review/queue`, `POST /review/answers` | `review/routes.ts`, `review/service.ts` |
| Prompt, accepted answers, form map and explanation of one sentence of a note (pure) | `review/items.ts` `targetOf` |
| SQL of the queue, day counts, answers, card updates, `ling` reads (lemma, form, trigger) | `review/repo.ts` |

All grading and scheduling go through `@app/srs` (`gradeAnswer`, `ratingForGrade`, `newState`, `schedule`, `replay`, `snapshotOf`, `isKnownStability`); the modules add no scheduler logic.

## How to run and test it
`pnpm test --filter api` or `pnpm check`. Tests (PGlite, mini dataset, mock gateway, fixed clock, one test database per file):
- `notes/port.test.ts`: the real port passes `runNotesSuite`.
- `notes/notes.test.ts`: word note from a reader capture (top form *mesta* first from `tat-8214994`, at most three sentences, one per form, card made at once, lemma set to learning); repeated id returns the stored note; second id for the same lemma returns the lemma's note; 409 for an id of another kind; 400 for an unknown lemma; phrase and case sentence notes, one note per exercise; fallback to the capture and then to the base form when a lemma has no sentence; a capture that is not a form of the lemma is ignored; list order, kind and text filter, paging, bad cursor; suspend (leaves the queue), content change of the same kind only; delete (204, repeat harmless, 404 afterwards, leaves deck and queue, the lemma can get a new note); isolation (B gets 404 on get, update and delete of A's note, sees none in the list, gets 409 when it reuses A's id, A's note unchanged).
- `review/review.test.ts`: one card through new → 1 min → 10 min → review (≥ 1 day) → lapse (relearning, 10 min), with the variant moving to the next sentence; a batch sent twice returns the same results and changes no row; a repeated id inside a batch counts once; an answer the phone marked correct but the server grades wrong (*brat* for *brata*) is stored as wrong with rating 1, and its attempt goes through `AttemptsPort` (`other_case`, `case_after_verb`, given case `nom`); a changed rating is kept (`overridden`); revealed is rated again; *mestá* for *mesta* is wrong, *Bráta* is close; a future time becomes the server time; an older answer from a second device replays the log and matches in-order delivery; a lemma becomes known (source `review`) once stability passes 21 days; queue order (learning, reviews oldest first, new cards with reader captures first, `limit`); new and review caps across the 04:00 day boundary of a New York learner; isolation (B's queue shows none of A's cards, B's answer for A's card is not stored and changes nothing, B cannot reuse A's answer id: 409).
- `review/sync.test.ts`: fast-check property (25 runs): random answers (ties in time allowed) delivered as one ordered batch or as a random permutation split into random batches give the same card, equal to `replay` of the log in time order.

Every response is validated against its contract schema by the route helper in tests (a mismatch would be a 500), and the tests parse them with the schemas as well.

## Differences from the specification, and why
- **Queue counts follow B7's "Rules of Today"** (as the build lead asked): learning cards due now without a cap; review cards due now capped at `dailyReviewLimit` minus the reviews in today's learner day of cards first reviewed before today; new cards capped at `dailyNewLimit` minus cards whose first review falls in today. Suspended cards, suspended or deleted notes do not count. `counts` are totals for today; `items` are cut at `limit`.
- **An answer for a card the learner does not own** (another learner's, or an unknown id) is skipped: not stored, no result, the batch still answers 200. A 404 for the whole batch would leave a client's outbox stuck forever, and the shared contract test calls the endpoint with an example card id a fresh learner does not own. Nothing about the other learner's card is revealed or changed (tested). The deck endpoints with a path id answer 404 as specified.
- **`POST /notes` with an id another learner holds** answers 409 `conflict` (`insert … on conflict do nothing`; RLS hides the row), not 404.
- **Variant choice** (open in the docs): one sentence per top form in `top_forms` order, then other sentences of forms not yet covered, at most 3. The capture becomes a variant when its blank is a form of the lemma that no chosen sentence covers (it replaces the third dataset sentence); with no dataset sentence the capture is the only variant; with neither, the base form itself is the variant (`sentenceSk = lemma`, `sentenceEn = gloss`). The card's `variant_cursor` is the number of its reviews modulo the number of variants, so it is the same in any delivery order.
- **Accepted answers of a word sentence** are the sentence's form plus every form of the lemma with exactly the same case tag (*človeku* / *človekovi*). Phrase answers are the blank text and `textSk`; phrase notes have an empty form map.
- **`explain.triggerLabel`** is `<trigger lemma> + <case name in English>`, e.g. `vidieť + accusative`.
- **Grading**: `revealed` comes only from the client; every other grade is the server's. Rating = the learner's rating when `overridden`, else `ratingForGrade(serverGrade)`. `review.diagnosis` stores `{ diagnosis, clientGrade }`.
- **Times**: an answer time in the future is set to the server time, and a time before the card was made is set to the card's creation time (the scheduler cannot go back past a new card).
- **Scheduling**: new answers later than the whole stored log are scheduled one by one from the stored state; otherwise the card's whole log is replayed (`replay`, created at the card's creation, ordered by time then review id). Results carry the card state after the whole batch, so a repeated batch returns identical results. Cards are locked (`for update`) before answers are checked, so two devices wait for each other. Profile retention (a `real`) is rounded to 4 decimals before scheduling.
- **Attempts**: one per new case sentence review, id = the review id (so repeats are skipped), `source: 'review'`, `sourceRef` = review id, `correct` for grades `correct` and `close` (only accents differed; with strict accents close never happens).
- **Lemma status**: a new word note sets the lemma to `learning` when it was missing, `unknown` or `ignored` (source `reader`, `triage` for the words track, `manual` otherwise); known lemmas stay known. A lemma goes to `known` (source `review`) when its word card's stability passes 21 days; it is not set back on a lapse.
- **New card order**: `new_ord` = tier × 10¹³ + creation time in ms, with tiers reader and manual 0, declension and tutor 1, words 2.
- **`POST /notes` for a word** calls `ports.dictionary.ensureGlosses` before the transaction opens (never inside it); a failure there (budget, model) does not stop the note, whose gloss is then empty until the lexicon has one. Inside the transaction both modules read `ling` from their own `repo.ts`, not through the lexicon ports.
- **Deleting a deleted note** answers 204 (repeats are harmless); an unknown id answers 404. Suspending a note suspends its card too. A word note keeps its lemma (409 on a content change to another lemma); a content change of another kind is 400.
- `NotesPort.suspendNote` on an unknown or deleted note does nothing. Notes list text search (`q`) is a case-insensitive substring match on lemma, phrase, cue, gloss and sentences, not accent folded.
- New cards carry `newState(createdAt)` as `scheduler` (the F2 example shows `null`), so the client can always `parseSchedulerState(item.scheduler)`.

## Known gaps and follow ups
- The queue counts run four count queries per call; fine for one learner's deck, worth an index review on a large deck (`card_user_state_due_idx` covers the queue reads).
- `GET /notes/:id` returns the last 20 reviews (`DETAIL_REVIEWS`).
- A changed `desiredRetention` is used for new answers only; older states are not rescheduled unless a replay happens.
- Not run against real Postgres (PGlite only). `select … for update` on the card/note join locks both rows; the `authenticated` role has update on both.

## Notes for packages that depend on this one
- **B5, B6, B9**: call `ports.notes.*` inside your `withUser` transaction. `createWordNote` builds the content itself from `ling` (pass `context` for a capture); it returns the lemma's existing live note when there is one. `createCaseSentenceNote` returns the existing note of `content.exerciseId`. `setLemmaStatus` is one upsert for the whole list; `known_at` is kept when a lemma was already known.
- **B7**: `/review/queue` counts use exactly the "Rules of Today" definition; `today.test.ts` compares them.
- **M2 / I1**: `POST /review/answers` results hold the card after the batch for every answer of that card; replace the local card with it. Answers for unknown cards come back without a result; drop them from the outbox once the batch answers 200. `ReviewItem.scheduler` is never null.
- **I1**: answer and attempt rows share ids; the attempt's `sourceRef` is the review id.
