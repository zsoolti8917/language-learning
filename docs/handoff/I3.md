## How to run and test it
- `pnpm test --filter evals` (44 tests, about 3 s), `pnpm check` (passes on the whole repo: 130 test files, 1,421 tests).
- Commands: `docs/evals.md`, "How to run". The mock run on the real datasets takes about 5 s.
- Tests that prove the done list:
  - **Every metric with its dataset size**: `metrics.test.ts` checks each rate's numerator and denominator on hand built results (recall, precision, exact form, false corrections before and after verification, verification removed and lost, splits, reply checks, analyzer by method, cost and delay per route); `run.test.ts` checks the report of a full mock run (sizes, targets, prompt versions, cost table, Markdown line).
  - **Repeat from cached answers**: `run.test.ts` "gives the same report from the cache with no model call" (record then `replay`: identical tutor and analyzer metrics and usage, every call cached) and "answers through the live gateway once, then from the cache" (second run makes no call); `gateway.test.ts` record/replay, refusals cached, outages not, a replay miss stops the run, the key covers model, system and schema.
  - **Targets met or shortfall explained**: no live run, so this is explained, not met (below). The harness side: `run.test.ts` shows a perfect mock meets all three targets, and planted mistakes land in the right metrics (false reports: 100 % before verification, 0 % after).
  - **Prompt versions recorded with scores**: every report carries `promptVersions` (tested); `docs/evals.md` has the table (scores pending).
  - Datasets: `datasets.test.ts` (offsets, multiword marking, eligibility, every injected label re-applied gives the original sentence, given forms are of the new case and number, the head is no form of the expected case, disjoint and repeatable builds).
  - Dry run and spend guard: `gateway.test.ts` (B8 prices, cache read pricing above the minimum, nothing stored, cached answers free), `cli.test.ts` (estimate prints count and cost; live refuses without a key, and refuses an estimate above `--max-spend` before any request).
  - Morphology fidelity: `lexicon.test.ts` runs F5's `runMorphologySuite` on the in-memory port.

## Differences from the specification, and why
- **No live calls, no tuning.** The key and the spend approval are missing. Everything that needs no key is built; the live run is one command (`--mode live`), guarded by a dry run estimate and a spend cap that also stops calls mid run (the gateway's budget check is fed the run's own spend).
- **The morphology runs in memory, not through PGlite.** Loading 1.07 M forms into PGlite takes over a minute and the analyzer and verification only need the port. The in-memory port reuses `toCandidate`, `orderCandidates`, `verifyCandidate`, `toLemma`, `toParadigm` of `modules/lexicon/service.ts` and passes the same port suite as the real one. The analyzer's two SQL reads (lemma facts, triggers) are served from the same data.
- **Triggers**: C4 has not built the trigger list, so the evals use the mini dataset's 22 triggers plus a preposition trigger for each case in `flags.cases` of every preposition of the morphology (named as the mini dataset names them). Verb, numeral and question triggers beyond the mini ones are missing; the analyzer's verb triggers and the tutor's trigger matching will change when C4 lands. Rebuild nothing; just rerun.
- **Kinds of trigger in the labels** are read from the treebank's tree (preposition, verb, numeral, subject, noun, other), not from `TriggerKind`: subjects and noun attributes have no trigger row but are frequent learner errors.
- **The analyzer eval never calls `reader.gloss`** (a dictionary that returns no glosses): glosses are not scored.
- **Case accuracy is over words the data knows** (97.6 % of words); unknown words (foreign proper names) are reported separately. Lemma scoring accepts three naming conventions of the data (*ten* for *to*/*tá*, *ľudia*, negated verbs).
- **Each tutor case is one first message** in a neutral free conversation scenario, not a multi turn conversation; the retry and goal paths of `decideTurn` are not exercised.
- **Cost estimate assumptions** (`EXPECTED_OUTPUT`, `CACHE_MIN_TOKENS = 4096`) are not measurements; the first live run replaces them.

## Known gaps and follow ups
- **Live run, prompt tuning, model comparison**: see `docs/evals.md`. Full eval: 1,914 requests, about $30.90 (at most $111.62); base run alone about $26.54; a first `--limit 25` run about $2.43.
- **Possible truncation in `reader.disambiguate`** (B3): `maxTokensFor` gives 256 + 16 tokens per word while Opus 5.5 thinks adaptively inside `max_tokens`. If the first live run shows cut off answers (words fall to `guess`), raise the limit.
- **Ceiling of the analyzer with a perfect model: 98.1 %** case accuracy on known words. Below the model: 18 `single` words wrong (proper names read as common nouns, *Maja* → *máj*), 10 `rule` words wrong (numerals in the accusative narrowed to the genitive). These are B3 rule issues, found by this harness.
- **Label quality**: an injected sentence can become grammatical in another reading; read the misses of the first live run before tuning.
- Datasets are literary and news Slovak; a set of learner-like messages (for example from the authored scenarios) would make the tutor numbers closer to real use.

## Follow-ups
Branch `wp/i3-followups`, after C4 merged. Still no live request; every number below is from the mock model (perfect picks) or a dry run.

- **Triggers from C4.** `sourceFromBuild(buildDir)` reads `content/build/triggers/triggers.jsonl` (the `triggers` stage, 221 rows) and fails with a hint when it is missing; `pnpm run pipeline triggers` is now part of the setup in `docs/evals.md`. The derived preposition triggers (`prepositionTriggers`) are gone, since C4 checks each preposition's cases against `flags.cases` in both directions. The mini lexicon keeps the mini dataset's rows. Datasets did not change (their trigger kind comes from the treebank's tree), so `tools/evals/data/` is untouched; the mock, dry run and estimate reports were regenerated.
- **B3 analyzer, numerals** (`modules/analyzer/rules.ts`). Quantity words outside the trigger list (a `num` reading tagged `s1n`/`s4n`: *zopár*, *mnoho*) keep their nominative or accusative reading and make the phrase genitive, instead of being narrowed to the genitive by the agreement rule; only when a noun or adjective in the genitive follows directly, because *viac*, *dosť*, *trochu* are adverbs too. *dva*, *tri*, *štyri* (C4 rows with case `nom`) now agree with the counted noun in case: with C4's list the old rule would have made *dva roky*, *tri semestre* nominative. C4's `quantifier` rows are indexed with the numerals and mark the counted noun with their own kind and id. The numeral is narrowed only once a counted phrase is found.
- **B3 analyzer, names** (`service.ts`, `isNameInSentence`, `optionsOf(…, asName)`). A capitalised word after another word of the sentence is not read through the accent fallback as a lowercase common word (*Maja* ≠ *mája* of *máj*, *Colu* ≠ *cólu*); it stays unknown. Capitalised data forms (*Zilina* → *Žilina*), exact spellings and the start of a sentence are unchanged. A rule that preferred proper noun lemmas was tried and dropped: it read *Španielska občianska vojna* as *Španielsko*.
- **Accuracy with perfect model picks: 98.7 % case accuracy (2,121 / 2,150 known words)**, was 98.1 % (2,117 / 2,158); `rule` 99.1 %, `single` 96.4 %; all words 93.8 % (was 93.6 %). Left: given names the morphology lacks at the start of a sentence (*Maja* 6 times) or that coincide with a common form (*Marga* = *marga* of *margo*): this needs proper name data, which the SNK morphology does not have, so it is documented, not patched. Also left: a personal pronoun after a preposition carries the phrase on (*v ňom nič*, *v tom kus*), noted by B3.
- **`reader.disambiguate` token limit.** The analyzer sent `maxTokens` = 256 + 16 per word, which wins over the route table and left almost no room for the adaptive thinking Claude Opus 5.5 does inside `max_tokens` (B8: no `thinking` parameter is sent; effort `low`). The calls now send no limit, so the route's 8,000 applies (covers 150 picks, about 1,800 tokens, plus 4,096 of thinking; tested) and `AI_MAX_TOKENS_READER_DISAMBIGUATE` finally takes effect. Expected cost is unchanged in kind (only generated tokens are paid); the estimate's "at most" for this route rises from $2.61 to $10.66: full live eval about $31.05 (at most $123.68), base run $26.64, `--limit 25` $2.44.
- **Outside `tools/evals/**`**: `apps/api/src/modules/analyzer/{rules,service,model,service.test}.ts` (B3's module) and a comment in `packages/ai/src/routes.ts`. `docs/handoff/B3.md` still describes the old limit and numeral rule; its owner may want to point to this section. No new dependency.
