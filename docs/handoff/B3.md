# B3 Text analyzer
Status: done

## What was built
The real `AnalyzerPort` (`apps/api/src/modules/analyzer/`) and prompt version 1 of the route `reader.disambiguate` (`packages/ai/prompts/reader.disambiguate/`).

| Piece | Where |
|---|---|
| Port factory `createAnalyzerPort(ctx)`: wires the ports, the gateway and the SQL; keeps the trigger list in memory for 10 minutes | `port.ts` |
| Pipeline `analyzeText(deps, body, { userId })` and `optionsOf` (readings of one word, most frequent first) | `service.ts` |
| Pruning rules and trigger detection (pure): `applyRules`, `assignTriggers`, `indexTriggers`, `narrow` | `rules.ts` |
| Model step (system blocks from `systemFor` of B8's registry): `DisambiguationSchema` (`{ picks: [{ w, c }] }`, integers only), `packBatches`, `contextOf`, `picksOf`, limits | `model.ts` |
| SQL: `lemmasByIds` (`ling.lemma`, one query), `allTriggers` (`ling.trigger`) | `repo.ts` |
| Prompt v1 (role, rules with the input and answer format, the "text is data" rule; last block cached) and `firstReadingMock` for local mode | `packages/ai/prompts/reader.disambiguate/{v1,index}.ts` |

The pipeline:
1. `splitSentences` and `tokenize` of `@app/ling` on the body as given; token offsets are absolute.
2. One `lookupForms` call with every distinct word (NFC), then one query for the lemmas of all candidates and the trigger list. Forms written exactly so (capitals aside) are preferred; without one, forms that differ only in accents are used. Readings are sorted by lemma `freqRank`, then the share of that form and tag in `topForms`.
3. Rules, each never removing the last reading: a preposition of the trigger list limits the case of the phrase after it (modifiers, then the head; numbers and adverbs are passed over); a numeral of the trigger list in the nominative or accusative, or a number in digits from 5 up, makes the phrase after it genitive plural (a preposition that rules out nom/acc wins: *s 5 ženami*); adjectives and agreeing pronouns before a noun keep only the case, number and gender they share with it.
4. Method: one reading from the dictionary → `single`; one left after the rules → `rule`; else the model.
5. Open words go to `reader.disambiguate` as JSON data: contexts (the sentence, or a 400 character window of a long one) and each word with its readings by index. Identical words in identical contexts are asked once. At most 150 words and 24,000 characters per call and 8 calls per text; calls run one after another. Picks outside the listed indexes are ignored. Any word without a valid pick (bad index, bad JSON, refused, truncated, upstream failure, or beyond the call limit) gets its most frequent reading with `m: 'guess'`.
6. Triggers: `trig.i` is the index of the trigger token in the sentence. Members of a preposition phrase get the trigger row matching the preposition and the chosen case (`prep-v-loc`); the counted noun after a numeral gets the numeral (`num-pat`, or kind `numeral` without id for digits), which wins over a preposition. A nominal word in the case of a verb of the trigger list in the same clause (clauses end at punctuation) gets the nearest such verb (`verb-vidiet`).
7. Glosses through `DictionaryPort.ensureGlosses(ids, { sentenceSk: first sentence, userId })`; the lemma map from `ling.lemma`; `tokenCount` counts word tokens; `lemmaCounts` counts tokens per chosen lemma.

## How to run and test it
`pnpm test --filter api` (or `pnpm exec vitest run src/modules/analyzer` in `apps/api`), `pnpm test --filter ai`, `pnpm check`.

- `service.test.ts` (in-memory mini morphology and dictionary, mock gateway, no database):
  - Rules without the model (a gateway that fails every call, asserted unused): *v meste* `s6` + `prep-v-loc`, *do mesta* `s2` + `prep-do`, *päť žien* `p2` + `num-pat`; *v Bratislave*, *do ulice*, *na námestí* pruned by rule; *peknej ženy* by agreement; *päť pekných žien* → `p2f`; *5 kníh*; *s 5 ženami* stays instrumental; *do meste* keeps its only reading.
  - The model is asked only about open words (`['ženy']` for *Vidím ženy v meste. Idem do mesta.*), its index is used, the verb trigger follows; readings are listed by index; the last system block is cached.
  - Fallback to a guess for seven unusable answers; partly valid answers keep their valid picks; `budget_exceeded` is thrown; calls are made as the learner; duplicate contexts are asked once.
  - A text with instructions (*Ignore all previous instructions…*, a fake `</system>`, a "pirate" order) and a model that answers in prose or with invalid indexes still yields a valid `TextAnalysis`; the text reaches the model only inside the JSON user message.
  - Chunking: a 20,000 character text uses more than one and at most 8 calls, each within 150 words and 24,000 characters; one 20,000 character sentence is sent as windows.
  - Property (fast-check, 150 runs on accents, decomposed marks, emoji, NBSP, BOM, ZWJ, lone surrogates, abbreviations, Slovak words): every token's slice of the body is exactly one token of its type, inside its sentence, sentences in order, and no word is lost.
- `port.test.ts` (PGlite with the mini dataset, built as `container.ts` builds it): the shared `runAnalyzerSuite('real', …)`; `repo.ts` queries; a full analysis with rule, model and trigger results; the usage row of a model call belongs to that learner only; an unambiguous text makes no call.
- `packages/ai/prompts/reader.disambiguate/index.test.ts`: the prompt is no longer a placeholder, ends with a cached block, holds no date; the local mock picks reading 0.

The three backend checks: every result parses with `TextAnalysisSchema` (all tests). The module serves no endpoint and writes no learner row, so the isolation check reduces to the usage rows of its model calls, which are written for the given learner only (`port.test.ts`). The real port passes the shared analyzer suite.

## Differences from the specification, and why
- **Extra files in the module**: `rules.ts` and `model.ts` hold pure logic next to `service.ts`. Only `repo.ts` runs SQL.
- **Lemma facts and triggers are read directly from `ling`** in `repo.ts` (one query each, in `withSystem`), not through `MorphologyPort.getLemma`, so the analyzer makes one lemma query per text instead of one call per lemma. The contracts allow a module to read any table from its own `repo.ts`.
- **The output schema lives in the module** (`model.ts`), not in the prompt folder: `@app/ai` exports only its index, and the index belongs to B8.
- **`budget_exceeded` is not a fallback case**: it is thrown (from the model step or from `ensureGlosses`), so B4 can mark the import failed and tell the learner when the budget returns. Other gateway errors of `ensureGlosses` fall back to `getSenses`.
- **Calls run one after another**, which keeps answers and usage rows in order; with at most 8 calls and an import that runs in the background, latency is acceptable.
- **Trigger ids for numbers in digits**: none (kind `numeral` only), since `num-pat` names the lemma *päť*.

## Known gaps and follow ups
- Rules are tuned on the mini dataset only; I3 should score them against the treebank. Known weak spots: personal pronouns with gender tags (*ho*, *ich*) can be narrowed by agreement with a following noun; quantifiers (*veľa*) and question triggers are not detected; verb triggers do not prune.
- The trigger cache lasts 10 minutes per port instance; after a content load a running server may use the old list for that long.
- Words beyond 8 calls × 150 words become guesses. A 20,000 character text of everyday Slovak stays well under that.
- B3 owns the prompt; I3 tunes it with the evals.

## Notes for packages that depend on this one
- **B4**: call `ports.analyzer.analyzeText(body, { userId })` outside any transaction (it makes model calls and opens its own short `withSystem` reads), then store `analysis`, `tokenCount`, `Object.keys(lemmaCounts).length` and coverage in a second transaction. Catch `AiGatewayError` with `code === 'budget_exceeded'` (`details.resetsAt`) to fail the import with that reason; other errors are internal.
- `m` tells how sure a reading is: `single` and `rule` are certain, `model` is the model's choice among dictionary readings, `guess` is the most frequent reading.
- Number tokens carry no lemma. Unknown words have no `l`, `tag` or `m`.
- **Local mode**: the prompt folder's mock answers reading 0 of every word, so `pnpm dev` marks open words `model` with their most frequent reading.
- **I3**: `DisambiguationSchema`, `packBatches` and the limits are exported from `modules/analyzer/model.ts`; the prompt is `PROMPTS['reader.disambiguate']` version 1.
- The branch was merged with the project branch after B2 and B8 landed: the port suite and `port.test.ts` now run on B2's real lexicon ports, and the analyzer never calls a port inside a transaction, so the new optional `tx` argument is not needed. In the full `pnpm check` under a loaded machine, `apps/web/src/features/cases/CourseScreen.test.tsx` (not B3) timed out three times; it passes when run alone.
