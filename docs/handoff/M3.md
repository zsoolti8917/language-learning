# M3 Reader
Status: done

## What was built
Everything lives in `apps/web/src/features/reader/`.

| File | Holds |
|---|---|
| `LibraryScreen.tsx` | `/read`: the learner's texts (`GET /texts?archived=false`) and the starter texts (`GET /library`), each with a coverage ring; Add (`POST /library/:id/add`) or Open; loading, empty, error and offline states (offline lists the texts stored on the device) |
| `ImportScreen.tsx` | `/read/import`: title, a Slovak textarea with a character counter against 20,000, too long and empty errors, rate limit and offline messages, then the processing state with polling that slows down, the failure state with Try again (sends the text again under a new id and deletes the failed one) and Edit the text; opens the reader when ready |
| `ReaderScreen.tsx` | `/read/$textId`: title, coverage, the virtual text, the word sheet, phrase capture (bar above the tab bar and a sheet with an editable meaning), translation on request, reading position saved 2 s after scrolling stops; processing, failed (with retry), not found, load error and offline states |
| `VirtualText.tsx` | Virtualisation without a dependency: sentences are grouped into chunks of about 40 tokens that never cross a paragraph; only chunks near the window are rendered (at most 16), with spacers holding the full height; heights are estimated until measured; it reports the first visible sentence |
| `WordSheet.tsx` | The sheet from the stored analysis only: gloss, dictionary form with part of speech and gender, CaseBadge with number, the trigger in words ("After “do” comes the genitive."), a hint for a guessed reading, Translate the sentence, All forms (`/lemma/$lemmaId`), Select a phrase, Report a problem; footer Save, Known, Ignore |
| `analysis.ts` | Pure helpers: TokenText tokens per sentence, chunks, `wordInfo`, phrase spans, `pollDelay`, `TEXT_IMPORT_MAX_CHARS` |
| `data.ts` | `loadText` (server, stored on success, falls back to the stored copy on a network error), `mergeStatuses`, and the writes: `saveWord`, `setWordStatus`, `savePhrase`, `reportToken`, `translateSentence`, `saveProgress` |
| `hooks.ts` | `useText` (query with the slowing poll, `networkMode: 'always'`), `createText`, `useReimport` |
| `TextStatusViews.tsx` | Processing and failed views, `CoverageRing` |
| `messages.ts` | Every interface text of the feature (`defineMessages`) |
| `mocks.ts`, `mockAnalyzer.ts` | Stateful mock handlers (see below) and a tiny analyzer for the mock |
| `fixtures.ts` | Test data (example text, long texts) |
| `e2e/` | Playwright config and `reader.e2e.ts` |

Writes all go through the outbox, so they work offline: Save → `POST /notes` (word, `source: 'reader'`, `textId`, `context { sentenceSk, sentenceEn? , blank, tag? }`), Known and Ignore → `PUT /lemmas/:id/status`, Save phrase → `POST /notes` (phrase), report → `POST /reports` (`targetKind: 'analysis_token'`), position → `PATCH /texts/:id { progress: { sentence } }`. Save marks the lemma `learning` locally at once; status changes are written to the `lemmaStatus` table at once. A merger joins waiting `texts.update` items of the same text into one request. Translation calls the API directly (it needs the server) and is written into the stored analysis.

Word statuses: the server's `lemmaStatus` of the text replaces the local table, except for lemmas with a status write still waiting in the outbox, whose local status wins. An offline copy uses the local table.

## Differences from the specification, and why
- Coverage is shown with `ProgressRing` (the percent in a small ring), not as a bar, because the design system has no bar component.
- The import textarea is a plain `<textarea>` styled with `fieldClasses` from `ui`, because the design system has no multi-line field. It has `lang="sk"`, a label, and 16 px text.
- The reader's `<h1>` is the small "Reader" label, and the text's title is an `<h2>`. The shell's route tests (F6) look for an h1 named after the screen.
- The word sheet's report reference is `<textId>:<sentence>:<token>:<word>` in `targetRef`, because the contract does not fix a format. B4 or B7 can parse it.
- Translation runs from the word sheet ("Translate the sentence"), not from a button on each sentence, so the text stays clean.
- The mock handlers use their own copy of `mockEndpoint`. `src/mocks/handlers.ts` loads `features/*/mocks.ts` through an eager glob while it is still loading itself, so importing `mockEndpoint` from it into a feature's `mocks.ts` fails with "Cannot access before initialization".
- The F6 tests require the default mock answers to equal the contract examples. So the reader mock is seeded with the examples and answers each example request with the example's response: `library.list` is not overridden, and `library.add` only adds a side effect (the copy is kept under the example's text id).

## Known gaps and follow ups
- `notes.create` in the mock answers with the contract example (lemma 20) whatever was saved. The reader therefore registers no outbox applier for `notes.create`; the local status set at save time stands until the next server answer.
- Saved phrases (`TextDetail.phrases`) are not highlighted in the text.
- Archiving and deleting texts from the library are not in the interface, though the endpoints exist.
- Restoring the reading position on open scrolls to the estimated place, then to the sentence once it renders. I checked this only through the code, in no browser.
- The offline flow is proven in Vitest, not in Playwright. In mock mode the MSW service worker answers even when the browser is offline.
- Requested shared change (F6, `src/mocks/handlers.ts`): load feature mocks lazily, or move `mockEndpoint` and its helpers into a module that does not import the glob, so features can use the shared helper.
- F6's own Playwright config uses fixed ports with `reuseExistingServer` when not in CI. When several checkouts run at once it can test another checkout's build. Separate ports or `reuseExistingServer: false` would avoid that.

## Notes for packages that depend on this one
- Mock store: `features/reader/mocks.ts` exports `resetReaderMock()`, `readerMockStore()`, `MOCK_FAIL_MARKER` (`#fail`) and `MOCK_PROCESSING_POLLS`. It also answers `PUT /lemmas/:id/status` with the lemma and status that were sent, and records `POST /notes` word saves as `learning`. These two handlers apply in every feature's tests and in the browser mock. In the browser the store persists in `localStorage` (`mock.reader`).
- `lemmaStatus` table: the reader writes `learning` on save, and `known` or `ignored` on those actions. It overwrites rows of a text's lemmas with the server's statuses when it opens the text, unless a status write for that lemma is still in the outbox.
- I1: the reader expects `GET /texts/:id` to answer `processing` until the analysis is stored, and `lemmaStatus` to hold every lemma of the text that has a status. Tokens without `l` cannot be tapped.
