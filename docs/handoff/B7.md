# B7 Profile, today, stats and reports
Status: done with gaps

## What was built
All inside `apps/api/src/modules/profile/` and `apps/api/src/modules/reports/`. The F5 stubs are gone; `app.ts`, `container.ts` and every shared surface are unchanged.

| Endpoint | Where | Behaviour |
|---|---|---|
| `GET /me` | `profile/service.ts` `getProfile` | The profile (the route helper creates it on the first call). `desiredRetention` is rounded to 6 digits because the column is a 4 byte `real`. |
| `PATCH /me` | `checkUpdate`, `updateProfile` | Ranges come from the contract schema (`dayStartHour` 0 to 23, `dailyNewLimit` 0 to 1,000, `dailyReviewLimit` 0 to 10,000, `desiredRetention` 0.7 to 0.99, `wordsBandTarget` > 0). The time zone must be a name `Intl` knows, or the answer is 400 `body.timezone`; this check runs before any transaction opens. Only the fields sent change, and `settings` is replaced as a whole. `updatedAt` comes from the server clock. |
| `DELETE /me` | `checkLoginDeletion`, `deleteRows`, `deleteLogin` | It deletes the `app.profile` row in `withUser`, and every learner table cascades from it. It then calls `deps.profiles.forget(userId)`. After the transaction closes, in Supabase mode only, it sends `DELETE {SUPABASE_URL}/auth/v1/admin/users/{id}` with `apikey` and `Authorization: Bearer <SUPABASE_SECRET_KEY>`, using `fetch` with a 10 s timeout. A 404 counts as deleted. A failure or refusal answers 502 `upstream_failed`. A retry works: the profile is recreated, deleted again, and the login call is made again. In Supabase mode without a secret key it answers 500 `internal` and deletes nothing. In dev mode only the rows are deleted. |
| `GET /me/export` | `exportAll`, `repo.exportRows` | It returns `{ version: 1, exportedAt, profile, tables }`. `tables` has 13 keys (`userLemma`, `note`, `card`, `review`, `attempt`, `lessonProgress`, `text`, `conversation`, `message`, `tutorError`, `placement`, `aiCall`, `contentReport`). Rows are camelCase, timestamps are ISO, and `userId` is left out. The response carries `Content-Disposition: attachment; filename="slovak-export-YYYY-MM-DD.json"`. |
| `GET /today` | `today` | See "Rules of Today" below. |
| `GET /stats/summary` | `stats` | `reviewsPerDay` covers the 7 learner days ending today, oldest first, and correct means a rating of 2 or more. `retention30d` is the share of passed reviews (rating of 2 or more) among the reviews of the last 30 days whose card's previous review was at least 21 days earlier; it is null without such reviews. `words` counts `user_lemma` rows that are known or learning. `mastery` holds the buckets of `AttemptsPort.getMastery` that have attempts. |
| `POST /reports` | `reports/service.ts` `createReport` | A new report answers 201 `{ id }`, with `created_at` taken from the server clock. A repeat with the same content answers 200 with the stored id. The same id with other content is 409. An id another learner holds is 409 too (`insert … on conflict do nothing`; RLS hides the row). There is a limit of 30 reports per learner day (`DAILY_REPORT_LIMIT`), checked against all of the learner's `content_report` rows, including tutor disputes. Over the limit the answer is 429 `rate_limited`, and `retryAfterSeconds` runs until the learner's next day starts. |

Writes go only to `app.profile` and `app.content_report`. The module reads `card`, `note`, `review`, `user_lemma`, `lesson_progress`, `text`, `conversation`, `ling.lesson`, `ling.scenario` and `ling.lemma` from its own `repo.ts`, and reads mastery only through `ports.attempts.getMastery(tx)`.

### Rules of Today (`service.ts`)
- **`date`** is the learner day from `learnerDay(now, timezone, dayStartHour)`, as `YYYY-MM-DD` in the learner's time zone.
- **`review`**, from `queueCounts`. B1's queue must use the same definition:
  - `learning`: cards in state `learning` or `relearning` with `due_at <= now`. No cap applies.
  - `due`: cards in state `review` with `due_at <= now`, capped at `dailyReviewLimit` minus the reviews in today's learner day of cards first reviewed before today.
  - `new`: cards in state `new`, capped at `dailyNewLimit` minus the cards whose first review falls in today's learner day.
  - In all three, cards that are suspended, or whose note is suspended or deleted, do not count.
- **`continueText`**: the learner's text with `status = 'ready'`, not archived, and the latest `last_opened_at`. Null when none qualifies.
- **`nextLesson`**: `profile.currentLessonId` unless it is `completed` or `tested_out`, otherwise the first course lesson (by `ord`) that is not done. A lesson without a progress row is `available`. Null when every lesson is done.
- **`weakBuckets`**: buckets at level `weak` from `AttemptsPort.getMastery`, sorted by mastery ascending and then attempts descending, at most 3.
- **`tutorSuggestion`**: a `case_coach` scenario that targets the weakest bucket's case. If none exists, any scenario that targets that case. Without a weak bucket, the scenario with the fewest completed conversations. Ties go by `ord`.
- **`words`**: three bands of 1,000 ranks (`BAND_SIZE`, `BAND_COUNT`). The current band is the first one that still has a word that is neither known nor ignored. When every band is finished, it is the last band that has words. `target` is `wordsBandTarget`.
- **First run** (`placementDoneAt` null): `weakBuckets` is `[]` and `tutorSuggestion` is null. Reviews, the text, the first lesson and words still show. This matches M1's `TODAY_FRESH`, and M1 shows the placement card based on `profile.placementDoneAt`.

## How to run and test it
- `pnpm check` passes (771 tests and 1 skipped, see below). Run `pnpm test --filter api` for this package only. The tests use PGlite, the mini dataset and one test database per file, and make no network calls (`fetch` is stubbed with `vi.stubGlobal`).
- `profile/profile.test.ts` (23 tests): `GET /me` defaults; `PATCH /me` (fields, clock, time zone refused, 8 out-of-range bodies, range edges, empty body). Export: rows from every table for the learner and none of another learner's; a test checks that the 13 exported tables plus `profile` are exactly the tables of schema `app` in the catalog. `DELETE /me` in dev mode: no row of the learner in any table of schema `app` (the table list comes from `information_schema`), the other learner's rows are untouched, and `fetch` is not called. Supabase mode: URL, method and headers; the rows were already gone when the login call ran; 404 counts as success; a 500 or a network error gives 502 and a retry works; without a key nothing is deleted. An isolation test covers every profile endpoint.
- `profile/today.test.ts` (13 tests and 1 skipped):
  - A fresh account matches a hand-built `Today`.
  - A seeded learner in the middle of the course, in New York, matches a hand-built `Today`: date of the 16th at 08:30Z, current lesson `loc-sg`, weak `loc.sg.f` leading to `scn-coach-loc`, the text, band counts and the target.
  - A learner with everything done.
  - Review counts and caps across the day boundary: New York gives due 2, new 1, learning 1. The same rows in UTC give 3, 2, 1, and New York after 09:00Z gives 3, 2, 2.
  - Stats with hand-computed days and retention.
  - Pure helpers, including a learner day of 25 hours when summer time ends.
- `reports/reports.test.ts` (7 tests): 201, comment optional, repeat 200, conflict, validation, the 30-a-day limit with `retryAfterSeconds` and the day boundary of a New York learner, and isolation.

## Differences from the specification, and why
- **Agreement with `GET /review/queue`** is written as a test (`today.test.ts`, "agree with GET /review/queue"), but it skips itself while the queue still returns the F5 contract example. B1 is built in parallel, so the counts are proven against hand-computed numbers for now. The test runs on its own once B1 merges.
- **Isolation for `POST /reports`**: when learner B posts learner A's report id, B gets 409 `conflict`, not 404. A create cannot be a missing row, and the primary key is global. B never sees A's content. The `/me` endpoints have no ids, so their isolation test checks that B's answers hold nothing of A's and that B's deletion leaves A's rows.
- **Several rules the documents leave open** are fixed here and listed under "Rules of Today": first-run contents, band choice, the meaning of "correct" in stats, what counts as a mature card in retention, and the limit's count.
- The tutor's dispute rows count toward the report limit, because the table does not tell them apart from other reports.

## Known gaps and follow ups
- Not run against real Supabase. The admin call follows Supabase's documented `DELETE /auth/v1/admin/users/{id}` and sends the key in both headers, as `supabase-js` does.
- If the login call keeps failing, the rows are gone but the login stays. The client should retry `DELETE /me`, which is safe to repeat.
- `/today` runs about 9 small queries in one transaction. That is fine at personal scale, and none of them call the network.

## Notes for packages that depend on this one
- **B1**: make `GET /review/queue` `counts` follow the definition under "Rules of Today", using the learner day, `dailyNewLimit` and `dailyReviewLimit`, and the same exclusions. `today.test.ts` then compares the two automatically. If B1 needs another definition (for example, counting only reviews of review-state cards toward the cap), change `repo.dayActivity` and `service.queueCounts` together with it.
- **B5**: Today and stats read mastery only through `AttemptsPort.getMastery`. The hand-built tests use buckets that are all wrong or all right, so they hold for the recorder and for the weighted formula.
- **I1**: remove the skip condition in the agreement test once the queue is real, or keep it, since it no longer triggers. M1 shows Today's counts as `review.due`, `review.new` and `review.learning`.
- **F8**: account deletion needs `SUPABASE_URL` and `SUPABASE_SECRET_KEY` in the API's environment. Without the key, `DELETE /me` answers 500 in Supabase mode.
