# M2 Review session and deck

## What was built
Everything lives in `apps/web/src/features/review/`. No file outside it changed.

| File | Holds |
|---|---|
| `session.ts` | The pure session reducer: `buildSession` (learning steps, then due reviews oldest first, then new cards in server order, capped by the queue counts less what this device answered), `sessionReducer` (`start`, `type`, `submit`, `reveal`, `rate`), `remaining`, `consumedBy`, `schedulerStateOf`. Grades with `gradeAnswer`, schedules with `schedule` from `@app/srs`; a card in a learning step goes to `returning` and comes back when its minutes are up, before the next queue card. |
| `feedback.ts`, `Feedback.tsx` | The feedback model and its text: correct; close with the missed accents marked letter by letter; wrong with the typed form's case named in a sentence (`diagnoseForm` readings, every reading listed), the answer, the case the sentence needs and the trigger, each case also as a `CaseBadge`; revealed shows the answer. |
| `store.ts` | `loadQueue`: online, `outbox.syncNow()` first, then `GET /review/queue` (limit 200) into the local `reviewQueue` table; offline, on a network error, or while answers still wait in the outbox, the stored queue. `recordAnswer`: the card's new state into `reviewQueue`, the cap counts (`kv` key `review.consumed`), and the answer into the outbox (`review.submitAnswers`, merged into one batch with waiting answers). A stable `clientId` per device (`kv` key `review.clientId`). |
| `useReviewSession.ts` | Hook around the reducer: loads queue and profile (`strictDiacritics`, `desiredRetention` from `loadProfile`), stores each answer exactly once. |
| `ReviewScreen.tsx` | `/review`: the card (sentence with the gap, cue or gloss, English sentence), `AnswerInput` (kept focused), Check and Show answer, rating buttons Again, Hard, Good, Easy with the default marked and a hint; Enter submits, Enter again accepts the default, a tap on another rating commits that one (`overridden: true`). Loading, empty, done, error with retry and offline states, an offline and "waiting to be sent" line, a link to the deck. |
| `ReportSheet.tsx` | "Report a problem" on every card: a sheet with a comment; `POST /reports` through the outbox (works offline). |
| `DeckScreen.tsx` | `/deck`: search (debounced `q`), filter by kind (toggle buttons), paged list (`useInfiniteQuery`, key `['api','notes.list',…]`), load more; loading, empty, no match, error and offline states. |
| `NoteScreen.tsx`, `NoteEditSheet.tsx` | `/deck/$noteId`: label, gloss, kind and source; sentences with the hidden part and its case; schedule (state, due, stability, difficulty, reviews, lapses, last review); last reviews; Suspend/Resume, Edit (meaning; for a case sentence the English sentence, cue and answers) and Delete with a confirmation sheet. Suspend and delete also drop the note's cards from the local queue. |
| `format.ts`, `messages.ts` | Display helpers; every interface text (`defineMessages`). |
| `mocks.ts` | Browser mock of `GET /review/queue` (five case sentence cards built from the contract's example exercises, three due reviews and two new, with real scheduler states) and `POST /review/answers` (a card state per answer). |

## Differences from the specification, and why
- **Report target.** The contract's `ReportTargetKind` has no `note` or `card`, and `ReviewItem` carries no sentence or exercise id. Reports from a card use `targetKind: 'sentence'`, `targetRef: 'note:<noteId>/<variant>'`.
- **Learning ahead.** When the queue is empty but learning cards wait, the earliest one is shown before its time, so a session can end (as Anki's 20 minute learn ahead). With the 1 and 10 minute steps every waiting card is within that window.
- **ts-fsrs steps.** Good on a new card goes to the 10 minute step and Again to 1 minute (F4's scheduler); tests follow that.
- **Contract example scheduler.** The `review.queue` example's `scheduler` (`v: 'ts-fsrs@6/fsrs-7'`) is not readable by `parseSchedulerState` (`fsrs7.1`). A card without a readable state is scheduled from `newState` on the phone; the server's state replaces it after sync. The feature mock uses real states.
- **Offline reload in Playwright.** The mock build has no app service worker (F6), so the test keeps the shell files seen online and serves them while the browser is offline; API calls are answered by the mock worker as always.
- **`mocks.ts` is off under Vitest** (`import.meta.env.MODE === 'test'`), see the gaps below. The review tests install `reviewMockHandlers` or their own answers per test.
- **Own Playwright config** in `features/review/e2e/` because `e2e-app/playwright.config.ts` is F6's and matches only its two files.

## Known gaps and follow ups
Requested shared changes (not made here):
- **F6, `src/mocks/handlers.ts`:** a feature's `mocks.ts` cannot call `mockEndpoint`: the eager glob imports the feature module before `handlers.ts` finished its own imports (`ReferenceError: Cannot access '__vite_ssr_import_3__' before initialization`). M2 builds its handlers with `msw` directly on the same URL pattern. Fix: move `mockEndpoint` and friends to a module without the glob (for example `mocks/endpoint.ts`).
- **F6, `src/lib/api/client.test.ts`:** expects every endpoint of the shared mock server to answer its contract example, so any feature override breaks it. It could test `defaultHandlers` (`server.resetHandlers(...defaultHandlers)`) instead; then `mocks.ts` can stay on in tests.
- **F2:** a report kind for a note or card (or `exerciseId`/`sentenceId` on `ReviewItem`), and a `review.queue` example with a scheduler state `@app/srs` reads.
- Suspend, edit and delete need a connection (online mutations with an error toast); only answers and reports go through the outbox.
- The deck keeps its search and filter in component state, not in the URL (the route table has no search params for `/deck`).

## Notes for packages that depend on this one
- I1: the session syncs the outbox before every queue fetch and never fetches while answers wait, so a fetched queue never brings back cards answered offline.
- The local queue rows carry the phone's scheduler state after each answer; `applyCardSnapshots` (F6) replaces it with the server's after `POST /review/answers`.
- Kv keys owned here: `review.consumed`, `review.clientId`. `clearLocalData` clears them.
- M1 (Today): the review tab is `/review`; a start button only needs to link there.
