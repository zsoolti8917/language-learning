# M6 Tutor chat
Status: done

## What was built
All in `apps/web/src/features/tutor/`.

| File | Holds |
|---|---|
| `ScenariosScreen.tsx` | `/tutor`: scenarios (title in English and Slovak, goal, level, target cases as `CaseBadge`, times done, case coach label), conversations to continue, Start (`POST /tutor/conversations` with a `newId()`, the answer seeds the chat's query cache, then navigates). Loading, empty, error and offline states. |
| `ChatScreen.tsx` | `/tutor/$conversationId`: header with End, goal panel with ticks, message list, turn failure with "Send again", budget and offline notices, composer, dispute sheet, end summary. Loading, not found, error and offline states. |
| `chatState.ts` | The chat reducer: messages, error marks, goal ticks, budget, turn phase (`idle`, `sending`, `streaming`, `failed`). |
| `turn.ts` | `runTurn(api, { conversationId, clientId, content, signal }, dispatch)`: one stream turn → reducer actions; `prepareMessage` (NFC, trimmed). |
| `useChat.ts` | `useChat` (query, reducer, send, retry with the same client id, end) and `usePeek`. |
| `marks.ts` | `locateMark`, `splitMarks`: where an error underline sits in the learner's text. |
| `Messages.tsx`, `Goal.tsx`, `Composer.tsx`, `DisputeSheet.tsx`, `Summary.tsx` | The parts of the chat. |
| `messages.ts` | Every interface text of the feature (`defineMessages`), including a label per `ErrorType`. |
| `mocks.ts` | Mock handlers: a scripted conversation for `tutor.sendMessage` and its end summary (see below). |
| `e2e/playwright.config.ts`, `e2e/tutor.e2e.ts` | Playwright at 390 x 844 against the mock stream (Vite dev server in mock mode on port 5183). |

Behaviour:
- Stream: `analysis` gives the learner message its server id and underlines its errors; `delta` grows the reply; `done` replaces the reply with the stored text, shows a "Card added" chip per created note (link to `/deck/$noteId`), updates the goal ticks. `error`, a failed request, a stream that breaks off or an unknown event make the turn `failed`: the partial reply is removed (never half shown), the learner message stays with a dashed border, and "Send again" repeats the same `clientId` and content. A retry never adds a second learner message.
- Marks: `prompted` (wavy, "try writing it again", buttons Hint and Show the answer → `peek`), `self_corrected` (fixed), `corrected` (the form and its reason, "This looks wrong" → sheet with optional comment → `POST /tutor/errors/:id/dispute`), `disputed`. Each state is said in words and with an icon, not only by colour. `summary_only` errors are not shown in the chat. A prompted error never shows an expected form (the contract carries none).
- Translate on every stored tutor message (`peek` kind `translate`).
- `budget_exceeded` (as an event or as a 429 before the stream) and offline switch the composer off, with a notice; the typed text stays.
- Composer: `AnswerInput` (lang sk, no autocorrect) with the accent bar in capitals mode (`AccentBar allowUppercase`), Enter or Send, `maxLength` 1000 (`LIMITS.tutorMessageChars`), a counter in the last 100 characters.
- The list follows a growing reply while the learner is at its bottom (48 px slack), and leaves it alone once they scrolled up; sending jumps back down.
- End: `POST /tutor/conversations/:id/end` → summary text, goal reached or not with ticks, mistakes by type, corrections (given → expected, corrected sentence, reason, "not checked" for unverified ones), cards created, links to `/review` and back to `/tutor`. A conversation already finished shows its transcript without composer.
- Model output (tutor text, summary, explanations, peeks) is shown as React text only, `whitespace-pre-wrap`; never HTML or Markdown (tested).

## Differences from the specification, and why
- The screen headings stay the shell's `screens.scenarios` ("Tutor") and `screens.chat` ("Conversation") at level 1, because `routes.test.tsx` and `e2e-app/routes.e2e.ts` (F6) look for them. The scenario title shows under the heading.
- The chat reads its id with `useParams({ strict: false })`: route ids are `/tabs/tutor/$conversationId`, not the path F6's note shows.
- Error offsets are read as UTF-16 code units of the NFC text (what the contract example's `indexOf` produces). The client sends messages in NFC. If the slice does not equal `given`, the mark moves to the nearest occurrence of `given`, so it never covers wrong characters.
- `features/tutor/mocks.ts` builds plain MSW handlers instead of `mockEndpoint`: `src/mocks/handlers.ts` imports feature mocks through an eager glob while it is still loading, so calling `mockEndpoint` at module load in a feature's `mocks.ts` fails with "Cannot access … before initialization" (F6's note suggests exactly that pattern). `sseResponse` is used at request time only.
- Feature mocks win over the defaults everywhere, but `src/lib/api/client.test.ts` checks every endpoint against its contract example. So the tutor mock answers the example request (`clientId` = `EXAMPLE_IDS.learnerMessage1`) with the example stream, and `tutor.end` returns the scripted summary only for a conversation that played a scripted turn.
- The Playwright suite lives in the feature folder (`e2e/`) with its own config, since `e2e-app/` and `package.json` are not M6's. Results go to `apps/web/node_modules/.cache/tutor-e2e-results`.
- "This looks wrong" calls `tutor.disputeError` only; the contract says the server files the content report itself, so the client does not also call `POST /reports`.

## Known gaps and follow ups
- The conversation detail is fetched once per visit; turns are not written back into the query cache. Leaving the chat marks the query stale, so the next visit fetches it again.
- Card chips and the remaining budget come from the stream only; a reloaded conversation does not show the chips of earlier turns (the contract's `ConversationDetail` has no per message card list).
- The composer is a single line field (`AnswerInput`); no multi-line messages.
- Not tried on a real iPhone (keyboard and accent bar position).

## Notes for packages that depend on this one
- I1: the mock scripts in `mocks.ts` show the event sequences the client expects. The client sends `{ clientId, content }` with the content in NFC and treats `analysis.messageId` as the stored learner message id. A retry repeats the exact body; the server must answer it without storing the message twice.
- `done.tutorMessage.content` replaces the streamed text, so the stored reply is what the learner ends up seeing.
- An `error` event or a closed stream without `done` is a failed turn; the client offers a retry except for `budget_exceeded`.
